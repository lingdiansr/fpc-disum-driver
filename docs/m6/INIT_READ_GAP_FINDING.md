# 规格侧排查结论（去敏）：初始化期间不读 bulk 会导致零触摸

- 日期：2026-10-20；性质：**实现层排查结论**（研究侧在同一台设备上单变量复现），不改变交付包。
- 输入边界：只含设备行为、事件长度/计数与相对时间；**不含**真实图像、图像摘要、密钥、envelope、TLS 载荷、私有路径或源码。

## 1. 你们的交接包暴露的签名

你们 2026-10-20 的 `capture` 轮（run_id `53de50c1-…`）特征：

- 外层事件只有 **4 帧 / 209 B**（`code=5` 62/32/18/97）；
- **没有 `code=2` 的 `EVT_INIT_RESULT`**；
- `CMD_INIT` 完成后到 `TLS_INIT` 之前**没有任何 bulk 读取**（只有 `GET_DESCRIPTOR(18B)` 探活）；
- ARM 后 149 次 `timeout/0 B`，usbmon 里 0x82 没有任何 38 B 或 12 B 完成。

## 2. 我方单变量复现（同一台设备，无手指即可复现签名）

把参考工具的 bulk 读取**推迟到初始化之后**（其余参数完全不变：`0x08 → 0x50 → CMD_INIT(4B) → 重枚举 → GET_TLS_KEY → TLS_INIT → …`）：

| 组 | 初始化期间读 bulk | `EVT_INIT_RESULT` | 帧 / 字节 |
|---|---|---|---|
| 对照 | **读**（`CMD_INIT` 前启动，跨重枚举持续读） | 有 `code=2` | 5 / **247 B** |
| 实验 | **不读**（`TLS_INIT` 后才启动） | **无** | 4 / **209 B** |

⇒ **38 B 差额的成因确定**：`EVT_INIT_RESULT` 在设备 `CMD_INIT` 复位窗口前后发出；主机若未在此窗口排空端点，**该帧被设备复位丢弃**（不是主机解析/长度问题）。

## 3. 关键结果：同一改动会让 ARM 完全不上报

在本机上以"初始化期间不读"的读取时序做一次真实采集（操作者按提示按压）：

- 结果：`EVT_INIT_RESULT` 缺失、ARM 后 20 s 内 **0 次上报**、0 应用帧、退出码 1；
- 帧/字节与你们本轮完全相同（4 / 209 B）。

对照：同一设备、同一时段，只要初始化期间持续读（我方默认做法），今天多次采集均为 **17 帧 / 10,878 B、1 个 `9880B` 应用帧、退出码 0**，`ARM→finger-down` 0.1–7.2 s 不等。

⇒ **"初始化/重枚举期间不读 bulk"是足以单独造成零触摸的主机侧偏差**，与你们的零上报签名一致。

## 4. 建议的实现改动（行为层面，不含代码）

1. **bulk reader 必须在 `CMD_INIT` 之前启动**，并**跨重枚举持续存在**：句柄失效时换句柄，但**不停止读取、不推迟到 TLS 之后再开始**。
2. 重枚举窗口内收到的帧（尤其 `EVT_INIT_RESULT`）**必须保留并交付**，不得因换句柄而丢弃；确认方式：`init` 阶段应能记录到 `code=2`。
3. 保持现有顺序不变：`0x08 → 0x50 → CMD_INIT(4B) → 重枚举 → GET_TLS_KEY → TLS_INIT → TLS_DATA… → ARM → 等 FINGER_DWN → GET_IMG`。
4. **不要**为此添加固定等待、额外设备命令或 port reset；本结论只需"提前启动并持续读取"。

## 5. 仍未解释的部分（不要当成已结案）

- 我方另有一次（初始化通知**正常**、读取连续）仍然 0 上报的失败轮，随后提示音采集又成功；因此**接触/压力**仍可能是第二因素，本结论不覆盖它。
- 机制层面（设备是否因未排空初始化通知而拒绝进入可感知态）**未证实**；本结论只陈述"该读取时序偏差足以导致零触摸"这一可复现事实。
- 你们的 run 中 ARM 距最后 `TLS_DATA` 约 2.3 ms、初始化载荷为 4 B 全零：这两项在前序实验中**已被排除**为判别因素（详见 [`ARM_GATE_NOTE.md`](ARM_GATE_NOTE.md)）。
