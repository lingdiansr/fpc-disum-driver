## 1. 设备身份与枚举 `[CONFIRMED]`

| 属性 | 值 |
|---|---|
| 厂商 | Fingerprint Cards AB (FPC) |
| VID:PID | `10A5:9201` |
| bcdDevice | `0x0250` |
| bcdUSB | `0x0110`（USB 全速，bMaxPacketSize0=64） |
| 配置 | 1 个配置：总线供电 + 远程唤醒（attr=0xA0），100mA |
| 接口 | 1 个接口（num=0, alt=0）：class/subclass/protocol = `0xFF/0xFF/0xFF` |
| 端点 | **唯一数据端点：0x82 IN BULK，maxPacketSize=64，bInterval=0** |
| 其他端点 | **无**（无 bulk OUT、无 interrupt、无 isochronous） |
| 字符串 | iManufacturer=1, iProduct=2, iSerial=0（无序列号）、iInterface=5（接口字符串索引，见配置描述符原始字节的末字节 `05`） |
| 描述符原始字节 | 设备：`12 01 10 01 00 00 00 40 A5 10 01 92 50 02 01 02 00 01`；配置：`09 02 19 00 01 01 04 A0 32 09 04 00 00 01 FF FF FF 05 07 05 82 02 40 00 00` |

**推论（传输模型）**：
- 宿主→传感器：**仅控制传输（端点 0）**（无 OUT 端点）
- 传感器→宿主：**仅 bulk IN 0x82**（事件、命令应答、图像均经此端点）
- Windows 侧经 WinUSB 传输栈；Linux 侧等价 libusb：`libusb_control_transfer` + `libusb_bulk_transfer`（EP 0x82）

## 2. 系统角色与数据流

| 角色 | 专有实现（仅作边界说明，不属于净室输入） | 职责 | Linux 等价物 |
|---|---|---|---|
| 传输 | 主机侧厂商 USB 栈 | 控制传输、bulk IN 事件与应用数据 | libusb |
| 图像/事件消费 | 主机侧生物识别适配层 | 消费事件和图像 | libfprint `fp_dev` |
| 算法 | 主机侧专有匹配引擎 | 登记/识别/模板 | libfprint 自带（无需复刻） |
| 会话 | 主机侧会话服务 | 会话协调/持久化 | fprintd |
| 安全 | 主机侧密钥/TLS 服务 | envelope、TLS 通道 | 见 §8 |

**分层模型（三层必须分开，见 §3.2/§4.4）**：

```
L1 USB 包          : 控制传输 setup/数据阶段；bulk IN 0x82 的 64B 包流（包无帧边界含义）
L2 外层事件帧      : 12B 头 code/len/unknown + payload，按 len 跨包聚合（仅此层有帧边界）
L3 TLS 解密后应用消息: 设备→宿主方向；L2 的 payload 承载 TLS 记录，解密后得到应用消息
                     （应用头 + 像素/元数据），其内部布局见 §4.4
```

**已观测的数据流**：

- **Windows 成功会话（2026-10-14 运行日志）**：`ARM(0x02, wValue=1, 4B)` → 外层 `EVT_FINGER_DWN(code=6, len=12, value=0)` → `GET_IMG(0x09)` → `EVT_TLS`×12 → `GET_KPI` → `GET_DEAD_PIXELS` → `ARM` → `SESSION_OFF` → `ABORT(0x03)` → `SESSION_OFF`。设备侧图像经 TLS 应用数据下发，**没有** `EVT_IMG` 帧。
- **Linux 050（此前为历史黑盒；2026-10-15 已闭环）**：获授权的带手指采集**三轮均收到**外层 `EVT_FINGER_DWN(code=6, len=12, value=0)`，主机随事件发 `GET_IMG(0x09)`，设备以 11 个外层 `EVT_TLS` 帧承载，解密后得到 **1 个应用帧 `code=8 / 总长 9880B`（= 12B 帧头 + 12B 内层头 + 9856B 像素）**；两轮结构与长度逐项相同、像素内容 99.07% 字节不同（= 实时数据）。历史"收不到"已定位为**工具自身重复 `set_configuration` 的污染 + 手指按压未与 `ARM` 对齐**（帧级证据见 `docs/REVERSE_ENGINEERING.md` §2.15 #28–#31、#19）。
- 本仓库 CLI 的 `--flow windows` 仅表示"ARM 后立即 `GET_IMG`"的实验选项，**不是** Windows 等价的正确性证明；`--flow event` 表示"ARM 后等外层 finger-down 再 `GET_IMG`"。

## 3. 传输层

### 3.1 命令通道（宿主→传感器）`[CONFIRMED]`（ETW 实测 2026-08-15 + Linux usbmon 总线级复核）

- 命令经**控制传输**发送，全部为 **vendor 请求**：
  - 命令（OUT）：`bmRequestType=0x40, bRequest=<命令ID>, wValue=<模式/参数>, wIndex=0, wLength=<数据阶段长度>`
  - 查询（IN）：`bmRequestType=0xC0, bRequest=<命令ID>, wIndex=0, wLength=<请求的返回容量>`
- IN 的 `wLength` 是**请求容量**，不是实际返回长度：取 key 请求 `0x3E8`=1000 B，实测返回 121 B；`GET_STATE` 请求 72 B、**Linux 实测返回 72 B**。引用时必须写成“请求 N B”，实际长度以观测为准（`wLength_requested`/`bytes_returned` 逐条落盘）。
- `bRequest` **就是** §4 的命令 ID（`0x09`=GET_IMG、`0x02`=ARM、`0x01`=CMD_INIT 等实测吻合）。`0x40`/`0xC0` 是 `bmRequestType` 的取值（方向+类型），**不是**与命令 ID 相加的基址——写成"`0x40+0x09`"是错误表述
- **`CMD_INIT`(0x01) 需要 4B 数据阶段**（`wLength=4`；Linux 上 `wLength=0` 实测控制传输超时）。Windows 参考每轮发送变化的 32 位 `N`（研究侧事项）；**本规格给实现者的默认是 4 B 全零**——已证可完整采集（§10 行 2），实现**不需要**复现 `N`/`N+1`/`N+2`。
- **电源观测**：设备空闲约 2 s 可能被 USB autosuspend 挂起。应记录策略/状态；附录 C 成功轮使用 `power/control=auto`，因此不能把强制 `on`、修改 udev 或禁用挂起列为已证实的采集前置，也不能仅凭挂起状态归因当前超时。电源策略调试不作为本轮 M6 可用性证明。
- **速率需分两层描述**：设备描述符声明 `bcdUSB=0x0110`（USB 1.1 / Full Speed），而实际协商结果为 **High Speed 480Mbps**（Linux `sysfs speed=480`，`/sys/kernel/debug/usb/devices` 显示 `Ver= 2.01`）`[CONFIRMED]`。实现不得以 `bcdUSB` 推断实际速率；bulk 端点 `maxpkt=64` 与速率无关

### 3.2 数据通道（传感器→宿主）`[CONFIRMED]`

- **唯一端点 0x82 IN BULK，maxPacket 64，interval 0**
- 事件、命令应答、图像均复用该端点
- **事件帧结构（Linux 黑盒实测）`[CONFIRMED]`**：
  - 帧头 12B：`code(4B 大端) + len(4B 大端，含头全长) + 未知(4B)`
  - payload 紧随帧头；**帧长 > 64B 分多包传输（maxpkt=64），接收方必须按 len 跨包聚合**
  - 事件 code 值见 §4.2（ev_hello=0x01、ev_init_result=0x02、ev_tls=0x05 等均实测收到）
- **图像/应用数据传输**：`GET_IMG` 后设备以**外层 `EVT_TLS` 帧**（§4.4）承载 TLS 记录。成功参考运行出现 12 个 `EVT_TLS` 帧，`len` 为 `1009`×10、`529`×1、`81`×1（`len` 含 12B 外层头，12 帧合计 10,700 B），**这 12 帧外层合计即一次采集的 TLS 外层总量**；同一采集周期还含 12B 的 `FINGER_DWN` 外层帧（其 payload 为 0），故全部外层数据为 10,712 B，去掉外层头后的 TLS 字节流为 10,556 B（“10,556+12=10,568”是把外层帧长与 payload 混算，已废弃）；短包长度与各帧 `len mod 64` 一致。⇒ bulk 层**没有**独立的 12B 图像帧头；"12B 帧头 + 9856B 裸像素"没有参考运行证据。**2026-10-15 Linux 实测更新**：解密后的**应用帧自身**带 12B 帧头（`code=8, total=9880, unknown=0`），其 payload = **12B 内层头 + 9856B 像素**（两轮逐字节一致）；故"bulk 层没有图像帧头"仍成立，而"12B 帧头 + 9856B 裸像素"现已在**应用层**获得两次独立实测支持（内层 12B 的字段语义仍未定名）。
- **帧长边界是工程约定**：当前实现取 `12 <= len <= 65536` 并保留不完整字节。**设备侧的边界行为（非法长度、短包不等于帧尾、EIO、断连）尚未验证** `[PENDING]`，实现者必须按以下保守规则处理：非法长度视为协议错误并保留原始字节用于诊断，不得静默丢弃或重新对齐。
- **Linux 侧应用数据已取得（2026-10-15）**：带手指采集三轮均收到 `EVT_FINGER_DWN` 并解密出应用帧（§3.2/§4.5）。以下历史解释保留但已降级——当时（2026-10-15 复核）：最新无手指 run 中 EP 0x82 曾持续报告 EIO 而控制传输正常；进一步隔离显示该 EIO 由**主机侧重复的标准配置动作**触发，去掉该动作后同一流程可收到 `EVT_TLS` 帧并完成 server flight ⇒ 该“未取得”不得读作“设备未发送”，也不得作为设备 sensing 失败的证据。）

### 4.4 帧格式 `[CONFIRMED]`（独立运行观测）

- **外层事件帧**（bulk IN 0x82）：首 12B 帧头 = `code(4B 大端) + len(4B 大端，含头全长) + 第三字段(4B 大端)`，payload 随后。`code` 为 §4.2 事件 ID。实测收到：`EVT_HELLO`(0x01, len=12)、`EVT_INIT_RESULT`(0x02, len=38)、`EVT_ARM_RESULT`(0x03, len=12)、`EVT_TLS`(0x05)、`EVT_FINGER_DWN`(0x06, len=12)。
  - **第三字段 = 事件相关值字**：历史普查中 `EVT_INIT_RESULT`/`EVT_TLS`/`EVT_FINGER_DWN`/应用帧为 0，`EVT_HELLO` 曾为 4，`EVT_ARM_RESULT` 曾为 `0x64`（间歇可达，§10 行 3）。这是观测，不是允许值全集。实现必须原样保留；除 §16.1 明确规定的 `EVT_ARM_RESULT(value=0x64)` 失败策略外，不得仅凭第三字段裁决成败。
- **跨包聚合规则**：按实际交付字节数累积，收到前 8 B 即校验 `len`，合法时等到完整 `len` 字节再交付；可一次交付多帧，未满部分保留。**持续提交 64 B 请求并跨完成聚合是已成功的参考路径**；错误的是只读一次便停止整条流或把单次 USB 完成当整帧。大缓冲持续读也可用，但不自动保证完整性。短包与 ZLP 只结束一次 USB 传输，均不是 L2/TLS/应用帧尾；ZLP 不追加字节，也不清空 partial。
- **完成状态与部分数据（工程契约）**：timeout 不是 `actual_length=0` 的证明。完成回调必须先取得 status、有效实际长度及其字节；`TIMEOUT` 且长度 >0 时先按序喂入已有字节、保留未满帧，再按事务 deadline 决定是否继续。已取消的操作不得因尾部数据变成成功，但须记录已收字节数、处理或明确弃用的 partial。若包装 API 隐藏实际长度，不能无条件映射成“成功空读”；需用能暴露完成长度的路径，或显式以“接收完整性未知”失败。公开 API 依据：[libusb 同步 I/O](https://libusb.sourceforge.io/api-1.0/group__libusb__syncio.html)、[异步 timeout/cancel](https://libusb.sourceforge.io/api-1.0/group__libusb__asyncio.html#asynctimeout)。非法长度立即报错、保留诊断，不逐字节重同步（向量 `outer-frame/length-11-rejected`）。
- **命令应答**：控制传输 IN 返回（`GET_TLS_KEY` 实测返回 121 B，其请求容量为 1000 B；`GET_STATE` 请求容量 72 B、**Linux 实测返回 72 B**（Windows 侧未取得完成正文））；控制传输 OUT 返回 ACK/状态。
- 命令帧（宿主→传感器）：控制传输 setup 包即命令帧，无独立数据帧（§3.1）。
- **L2→L3 关系**：`EVT_TLS` 帧的 payload 是 TLS 记录字节流；解密后的应用消息格式见 §5。**不得**把 12B 外层头当应用消息头，也不得把外层 `len` 当像素起始偏移。

### 4.5 状态机（实测序列）

**录入**（16 次采样，~1s/次）`[CONFIRMED]`（**注**：此处 `[CONFIRMED]` 只指“该序列被观测”，`wValue=2` 的**语义**未验证，见 §16.4）：
```
SESSION_OFF(0x12) → ARM(0x02, wValue=2) → [GET_IMG(0x09) → GET_KPI(0x0C IN,28B) → GET_DEAD_PIXELS(0x0A) → ARM(2)]×16 → END_ENROL(0x13) → SESSION_OFF(0x12)
```

**验证**（锁屏实测）`[CONFIRMED]`：
```
ARM(0x02, wValue=1) → GET_IMG(0x09) → [GET_DEAD_PIXELS(0x0A) + GET_KPI(0x0C)] → ARM(1) → GET_IMG → SESSION_OFF(0x12)
```

**初始化**（独立参考运行）`[CONFIRMED]`：
```
枚举(GET_DESCRIPTOR/GET_STATUS) → 0x08(wV=0x0010, wLength=0) → GET_STATE(0x50 IN wL=72，请求容量)
  → CMD_INIT(0x01, wV=0x0001, wLength=4, Windows payload=`N`, e.g. `0f0e170c`; Linux 等价生成/复放未成功) → GET_TLS_KEY(0x0B IN, wLength=0x3E8→121B)
  → [设备推 EVT_INIT_RESULT(0x02, len=38；payload 已保存于私有 run（本规格不引用其内容）)：与取 key 同一时段，日志先后会交错] → TLS_INIT(0x05, wV=0x0001)
  → TLS_DATA(0x06, wV=0x0001)×6（握手，与设备 EVT_TLS 交错）→ 会话态
```
独立参考运行给出的**设备事件位置**：`EVT_INIT_RESULT` 在 `CMD_INIT` 之后、`TLS_INIT` 之前，约与取 key 同一时段（多次运行间 `GET_TLS_KEY` 与该帧的日志先后会交错，不构成顺序契约）；其 payload 未被运行记录保存。`EVT_TLS` 的第一个载荷 50B 即 client hello。Linux 侧需在等价位置核对（§10 缺口 5）。

**采集（成功参考运行，逐帧）`[CONFIRMED]`**（同一 run 内相对时间）：
```
ARM(0x02, wValue=1, wLength=4)                        @0.72s
  → 外层 EVT_FINGER_DWN(code=6, len=12, value=0)       @2.06s   ← 手指触发，设备异步推送
  → GET_IMG(0x09, wLength=0)                          @2.06s   ← 紧随 finger-down（µs 级）
  → EVT_TLS×12（承载 112×88/9856B 图像）              @2.07–2.12s
  → GET_KPI(0x0C IN, 28B)                             @2.11s
  → GET_DEAD_PIXELS(0x0A)                             @2.11s
  → ARM(0x02, wValue=1, wLength=4)                    @2.29s
  → SESSION_OFF(0x12) → ABORT(0x03) → SESSION_OFF(0x12)
```
即：**`GET_IMG` 由 `EVT_FINGER_DWN` 触发**，不得用固定延迟代替。`ARM` 到事件/`GET_IMG` 的间隔含操作者响应、接触与设备处理，**不是**已测的“按下后检测延时”或 readiness 参数。触摸前发送 `GET_IMG` 的对照轮虽随后收到 finger-down，40 s 内仍无图像 TLS 数据，故请求必须在该事件之后发送；这不构成任何固定按压时限。
- **主体区分（2026-10-17 澄清）**：上面代码块里的收尾（`SESSION_OFF → ABORT → SESSION_OFF`）是 **Windows 参考驱动**的顺序；本规格给干净实现者的清理契约是 §16.3 的 `ARM_STOP → ABORT → SESSION_OFF`，三条命令的编码见 §4.1。两者主体不同，不得混用。

**Linux 050 现状（2026-10-15 已闭环）**：同一顺序在获授权的带手指采集下**3/3 轮**收到外层 `EVT_FINGER_DWN`，`GET_IMG` 后解密出 1 个应用帧（`code=8 / 9880B` = 12B 帧头 + 12B 内层头 + 9856B 像素），三轮结构与头部逐项相同、像素两两 99.07–99.25% 字节不同。"采集"这一步在 Linux 上已打通；像素区间/行宽/位深/坐标系均已定案或显式约定（§10 缺口 1、10 已关闭）。
- **提示与按压（操作规程，不是设备定时门槛）**：参考工具在 `ARM` 控制传输返回成功后打印提示行，外层脚本读到该行才启动通知/声音请求；不是提交时刻、声音实际起播或设备武装确认。建议在成功回调后提示操作者再按压并保持到完成/松开提示，便于复核时序；曾采用约 20 s 保持规程，**没有单变量证据证明必须 ≥10 s**。早按约 3 s 的一个零帧轮和提示对齐后的成功轮，不能推出“所有预先按住的手指一定不上报”，也不能把后续超时归咎于用户未按。已确认用户按压时，应保留人工反馈并继续检查接收、TLS、状态机与提示边界。`ARM+3.977 s`（历史轮）/附录 C 的成功轮间隔只表示主机日志的 `ARM→事件` 总时间。
- **`EVT_ARM_RESULT` 不门控触摸等待**：`ARM` 完成后直接接收并处理事件，不等待该通知作为“已武装”信号；已成功采集的帧集合中没有它。唯有收到 `value=0x64` 时按 §16.1 使本事务失败。

> **参考工作流是"每会话一次采集"**（**Windows 参考序列**；本规格只支持单次采集，见 §16.4）：`ARM → finger_down → GET_IMG → image → KPI/deadpixel → ARM → SESSION_OFF`。研究工具另有 `--cycles N`（默认 1）用于**验证**同一会话内多次采集是否可行；它属于工具能力，**不是**参考工作流的组成部分，实现者不需要它。第二次采集在同一会话内**已被验证为支持**（§16.4：一个会话两轮各出一张 9880B 图像），但参考工作流仍按**每会话一次采集**编排。

## 5. 图像获取（几何、像素参数与 Linux 侧封装 `[CONFIRMED]` 2026-10-15；物理朝向 `[约定]`）

**已确认（成功参考运行 2026-10-14）**：

- **触发**：外层 `EVT_FINGER_DWN`（code=6, len=12）到达后，主机立即发 `GET_IMG`；设备以 `EVT_TLS` 帧承载图像。
- **持续接收（工程契约）**：完成一次请求后继续提交，并始终按 §4.4 聚合；参考成功路径使用 **64 B 容量**的阻塞读、约 **200 ms** 完成超时（deadline 截断会略小），不是强制 4096 B 或 100 ms。timeout 是本次等待上限，**不是**每次读之前睡眠的周期；有数据可提前返回，所以 1000 ms timeout 本身不证明秒级稀疏读取。只读一次就停止不正确；连续 64 B 读和连续大缓冲读均须验证 status/actual_length/partial，不能只凭容量判定无损。
- **几何**：成功参考运行的初始化日志明确报告 `height: 88 width: 112`；同一成功运行在 `GET_IMG` 后的独立图像接收记录报告 `112/88/9856`。`EVT_INIT_RESULT` 的 26B payload 已于 2026-10-15 的 Linux 轮中被原样保存：偏移 4/6 处为大端 `u16` **112 / 88**（与几何一致），偏移 8..19 为固件版本串 `021.26.2.050`；其余字段语义未定（单轮证据），**不得**把 `u32[0,1022,273,112,88]` 当成该 payload 的已验证布局。可确认的契约仍是 **几何 = 112×88**，以及在 8-bit 灰度假设下对应 9856 个像素字节。
- **该次传输**：`EVT_TLS`×12（长度见 §3.2）；解密后为应用消息，**应用消息总长 9880B，其中像素 9856B**（差值 24B 为应用层开销；2026-10-15 Linux 实测 3 轮：这 24B = 应用帧自身 12B 帧头 + payload 内层 12B 头，三轮逐字节相同；**其首字段的映射已于 2026-10-15 定案（§10 行 11），其余字段语义仍未定名**）。
- **时序**：图像传输开始后主机发 `GET_KPI`(0x0C IN, 28B) 与 `GET_DEAD_PIXELS`(0x0A)。

**逐项结论（2026-10-15 复核：1–3 已定案/已复现，第 4 项仍**不得**假设）：**

1. ✅ **像素起始偏移（2026-10-15 定案）**：应用帧内偏移 **24** = 12B 应用帧头（`code=8, total=9880, unknown=0`）+ payload 内层 **12B 头**（三轮逐字节 `00002f11 00000000 00000000`），其后 9856B 像素；`--pixel-offset 24 --stride 112` 在 3 轮真实采集上均 `trailing_bytes = 0`（24 + 9856 = 9880 精确闭合）。注意 24B 仍是**两个可分别定位的 12B 头之和**，不是"一个 24B 头"。另：分析器的空间判据对偏移**不敏感**（offset 取 0 时三轮仍 `accepted=True`，ridge 0.922 vs 0.933），因此偏移只能由帧结构证据给出，**不得**用"分析器通过"反推偏移。内层 12B 的**字段语义仍未定名**，但 2026-10-15 的三组单变量已确立它**跟随 `ARM` 载荷、与 `CMD_INIT` 载荷无关**：(`init`,`arm`) = (`102f1117`,`112f1117`) → `00002f11 00000000 00000000`；(`00000000`,`112f1117`) → **同上（不变）**；(`00000000`,`00000000`) → **全零**。**已定案（§10 行 11，台账 #51）**：内层头首字段 = `ARM` 载荷**前两字节的小端 u16**（`112f1117`→`0x2F11`；`12345678`→`0x3412`；两者置零→全零），载荷第 3–4 字节无观测效果。**不得**据此命名设备语义。
2. **行序 / stride / 位深 / 坐标系（2026-10-15 定案 + 约定）**：
   - **行宽 112（stride = 112，无行尾填充）**：对 9856B 的**全部**整数分块逐一计算跨行相关 `vertical_correlation`（3 轮均值）：**112×88 最高 = +0.886**，而 88×112 = +0.008、176×56 = +0.007、56×176 = +0.012、28×352 = +0.046；跨行相关 ≥0.85 的**最小**宽度恰为 **112**。配合 `trailing_bytes = 0` ⇒ 行宽 112、无填充成立。**局限（必须写进实现假设）**：224×44（2× 合并）仍为 +0.615，故 vcorr 单独**不能**排除整数倍分块；112 的结论同时依赖 `EVT_INIT_RESULT` 的 u16 `112/88`（§5 上文）与上述相关性。
   - **位深 8-bit 灰度**：3 轮实测值域 44–255、单峰直方图、`stddev` 31–48，未见成对重复字节。
   - **坐标系（本规格约定；实现必须遵守）**：像素按**行主序**排列，原点 = 应用帧内偏移 24 的第一个字节；`x` 沿行递增 0..111，`y` 沿行递增 0..87；**不得**旋转、转置或翻转。**物理朝向（哪一条边是手指近端）未由数据确定**，因此不得声称与 Windows/WBF 的朝向一致。
   - 方向可验证性：合成水平/垂直斜坡在被测分析器上给出**相反**的轴统计量，随机与全零被拒绝（§15.5、`tests/test_analyze_capture.py`）。
3. ✅ **Linux 侧外层封装已复现**：历史采集样本为 **11 个**外层 `EVT_TLS`（`1009`×10 + `529`×1，合计 10619 B），解密得到完整 9880 B 应用帧。Windows 样本为 12 帧，多一条 81 B 记录。**仅凭这些元数据不能证明两种 TLS 内容只差分段**；额外记录语义未定，不要求固定帧数。实现按完整 TLS 字节流、解密帧结构及 §5 布局验收（§8、附录 C），不得硬编码 11/12。
4. **192×56 / 10752B 灰度缓冲**：这是 Windows 侧内部缓冲的历史观察结果。**"由线协议 112×88 重采样而来"仍只是推断**——两者尺寸不同不足以证明存在某种具体重采样算法。该缓冲与 Linux 实现无关，不得作为线协议格式依据。

**已解除阻塞（2026-10-15）**：Linux 会话在 `ARM` 之后收到 `EVT_FINGER_DWN` 并解密出应用数据；剩余工作是把像素布局/方向写成可验证契约（§10 缺口 1）。

## 6. 初始化序列 `[CONFIRMED]`（独立参考运行）

成功参考运行中的初始化顺序：

1. 枚举：设备/配置描述符与 GET_STATUS
2. vendor `0x08`（`wValue=0x0010`）— 状态指示类
3. `GET_STATE`(0x50, IN, 请求容量 72B；**Linux 实测返回 72 B**，正文存私有 run；Windows 侧未取得完成正文)
4. `CMD_INIT`(0x01, `wValue`=0x0001, **4B 数据阶段**；默认载荷 **4 B 全零**即可，已证可完整采集（§10 行 2）。Windows 参考每轮生成基值 `N`（`N+1`/`N+2`）属于**研究侧事项，不是实现必需**）
   - **可能发生的初始化重枚举（设备观测）**：本机曾在命令成功约 1.0–1.1 s 后离场、约 0.5 s 后以新地址回来；这些是样本时间，不是设备定时保证或固定等待值。另有成功参考轮的身份快照前后相同，且未留到离场/新 generation 证据（附录 C）；**不能将“每次必变地址”或“始终不重枚举”写成普遍规律**。早先两类观测差异的成因未定位，不能认定旧观测必因采样过早。
   - **重取设备（工程契约）**：提交前记录 `bus + 完整 port_numbers 链 + VID/PID/bcdDevice`。初始化阶段若旧句柄失效或确见离场，停止旧 I/O，等待回调完成并释放旧资源，以约 0.2 s 节奏在 **20 s 有界 deadline** 内处理设备列表/hotplug，重取同一完整物理端口链的匹配对象；fresh enumeration 不能由同一对象的两次缓存属性读取替代。探活及稳定身份只是可响应/稳定性的证据；若已观测旧 generation 离场，必须绑定回来后的新 generation，通常地址变化，但地址不是持久身份或活体证明。不能按 VID/PID 随意换到另一颗设备。
   - **无离场与阶段边界**：未观测离场且连接仍可通信时，不强制等待地址改变、不额外发 port reset；可继续既有 `GET_TLS_KEY`/TLS 流程，若旧句柄失效则按上一条重取。刚出现时 `open`/claim 失败可在同一 deadline 内重试；到期或无法确认对象归属则明确失败。正常初始化的重连豁免只在本次 `CMD_INIT` 初始化事务中有效，不能无限屏蔽 removal；ARM/采集后发生的异常断连/reset 按 §16.2/§16.4 失败，不自动恢复认证。真实 generation 变化时不得拼接旧连接的 partial/TLS 流；保留弃用长度及首因记录。两次身份快照一致本身不证明已完成新 generation 重连。
   - **重绑后的下一步**：若本次初始化的预期离场发生在 `CMD_INIT` 之后、TLS 开始之前，正确重取/claim 后继续第 5 步 `GET_TLS_KEY`，**不再次发送 CMD_INIT**、不额外 port reset。若已开始 TLS 后连接/generation 改变，丢弃该 TLS 上下文并以“初始化连接变化”使本次 open 失败，不尝试拼接旧握手；需要重试时由新事务重新执行 §6。generation 的记录定义见 C.4。
   - **初始化分类是主机事务状态，不是复位原因检测**：仅当已成功提交本次 CMD_INIT、尚未开始 TLS/ARM、仍在本次20 s重取窗口、候选同端口归属可确认、且没有显式 port reset 或窗口外异常的记录时，使用本节初始化重取分支；此时 generation 可记 unknown，不因缺少独立代际证明就自动转入异常恢复。该分类允许附录 C 的同地址恢复，但不宣称知道设备内部发生了什么。窗口外/采集中失效、外部 port reset 或归属无法确认则结束当前事务。
5. `GET_TLS_KEY`(0x0B, IN, 121B)
6. `TLS_INIT`(0x05, `wValue=0x0001`)
7. `TLS_DATA`(0x06, `wValue=0x0001`) ×N — 完整握手输出按 ≤64 B 分片；历史 ×6 与参考成功轮 ×4 都是样本，不是强制次数（§8、附录 C）
8. 会话态（ARM 等）

- **是否必须等待 `EVT_INIT_RESULT`**：**不需要**——它是通知而非门控；下面的"位置"只是观测，实现可继续 `GET_TLS_KEY`/`TLS_INIT`。
设备事件位置：`EVT_INIT_RESULT(0x02, len=38；payload 已保存于私有 run（本规格不引用其内容）)` 出现在 `CMD_INIT` 之后、`TLS_INIT` 之前（与 `GET_TLS_KEY` 属同一时段，日志先后会交错）；`TLS_INIT` 之后设备以 `EVT_TLS` 推送 50B client hello，随后与 `TLS_DATA` 交错完成握手。

Linux 050 无手指基线（2026-10-15，早期三次独立 run）：三次均成功完成 `CMD_INIT` → 121B envelope 校验 → `TLS_INIT` → server CCS+Finished；但三次都**没有**记录到 `EVT_INIT_RESULT(code=2)`。**2026-10-15 晚复核（决定性）**：该差异由**主机侧重复发出的标准配置请求**造成——去掉该动作后，Linux 同一流程完整跑通：收到 `EVT_INIT_RESULT`(code=2, len=38, payload 26B) + `EVT_TLS` 62/32/18/97B（与参考运行的初始化帧集合**逐项一致**）、server flight 完成、进程退出码 0（本机私有 run「b3」；无 `CMD_INIT` 的对照轮「a3」收到 4 个握手帧并完成握手；私有 run 定位见研究侧台账，不入交付包）。⇒ 参考运行的事件位置与帧集合**已在 Linux 复现**；会话阶段（`ARM` 之后）随后也已在 Linux 打通（3/3 授权采集，见 §4.5）。

Linux 侧注意：
- Windows 参考行为不是固定 magic（**研究侧事项，不是实现的必需条件**）：多轮观察到每轮不同的基值 `N`、验证轮出现 `N+1`/`N+2`。**本规格给实现者的 4 B 输入契约是"任意值，默认全零"**（§10 行 2）；Linux 侧不需要复现该序列，也**不得**把它当作前置条件。
- `GET_HW_UNIQUE_ID`(0x31) 未出现在初始化序列中；Linux 侧该请求返回 STALL，原因待解释 `[PENDING]`。

## 8. 安全通道（TLS / 密钥）`[CONFIRMED：TLS 强制；握手发生在驱动初始化阶段]`

**初始化期握手（Windows 运行时日志 2026-08-15 与 2026-10-14 一致）**：
```
GET_STATE(0x50 IN wL=72，请求容量；**Linux 实测返回 72 B**) → CMD_INIT(0x01, wV=1, wLength=4)
  → GET_TLS_KEY(0x0B IN, wLength=0x3E8→121B)〔同一时段：EVT_INIT_RESULT(0x02)〕
  → TLS_INIT(0x05, wV=1) → TLS_DATA(0x06, wV=1)×N（与设备 EVT_TLS 交错；×6 为历史样本）
```
- **会话期（录入/验证）不含任何 TLS 命令**——握手在驱动初始化时一次建立，会话内复用。
- 由此**推断**（非直接验证）：设备自身重启后宿主不重握手，通道可继续存活 `[INFERRED]`。未做过"设备重启后同会话继续采集"的对照实验，实现不应依赖该性质——建议在 `open` 时总是重建握手。

**握手协议细节（Linux 黑盒实测 2026-08-15）`[CONFIRMED]`**：
- 参数：TLS 1.2，cipher **PSK-AES128-CBC-SHA256 (0x00AE)**，纯 PSK 模式（无证书）。
- **PSK 派生**：`GET_TLS_KEY`(0x0B IN) 返回的 envelope 中有一段 AES-256-CBC 密文；**解密密钥 = `SHA256("FPC_SEALING_KEY\0")`**，IV 为全零；解得 PSK（长度见下）。**[来源（2026-10-15 复核，已定位）]**：这两个字符串常量与上述推导出自**公开上游**项目 `vrolife/fingerprint-ocv`（`https://github.com/vrolife/fingerprint-ocv`；以仓库当前状态为准，本规格不记录 commit）（公开仓库，页标 AGPL-3.0；研究侧保留的公开仓库早期副本（本机路径略）中的 `fpc.c` 头部标 `License: LGPL-2.1`、同目录 `drv.py`/`tls_key.ipynb` 为等价实现 ⇒ **以公开上游仓库的许可为准**）。本规格记录的是**接口事实**（已由黑盒互操作验证：与真实设备完成 PSK 握手），实现方如需复用该常量须自行核对上游许可；交付包只引用来源，**不分发上游代码**。
- **消息流（宿主为 TLS server 侧）**：
  1. `TLS_INIT`(0x05, wV=1) → 设备经 `EVT_TLS` 推送 **client hello**（载荷 50B：TLS 1.2 + 仅提供 PSK-AES128-CBC-SHA256 套件）。
  2. server → ServerHello + ServerKeyExchange（PSK identity hint 为空）+ ServerHelloDone。
  3. 设备 → ClientKeyExchange（**PSK identity = `Disum PSK`**，实测 9 B；RFC 4279 的 2B 长度前缀 + identity，**不是**空 identity——与早期研究笔记的"空 identity"记载相矛盾）+ ChangeCipherSpec + Finished；宿主可验证其 Finished 的 MAC。
  4. server → ChangeCipherSpec + Finished。
- **session_id**：已成功互操作的样例使用 **32 字节非空 session_id**；手工实现使用空 session_id 时设备无响应。**没有单变量实验证明"必须恰好 32 字节"**，因此规格只要求"**回送非空 session_id**"，**不要求**其长度等于任一主机字段（实测样例为 32 B）。
- **传输路径**：TLS 记录承载在 **外层 `EVT_TLS`（code=5）** 帧的 payload 中（宿主→设备方向用 `TLS_DATA` 控制传输，按 **≤64 B** 分片：单次 `wLength` = 本次记录长度，实测 64/24/64/27 等；分片边界不携带语义，接收方按 TLS 记录合并）。**不得**把 `EVT_TLS` 的 12B 外层头当作 TLS 记录头。
- **验收状态**：Linux 侧 `SSLv3/TLS read client key exchange / read change cipher spec / read finished / write change cipher spec / write finished` 全部成功且无 TLS alert ⇒ 设备的 `Finished` MAC 已被宿主独立验证，握手在密码学上完成。
  - 这不等于对端已进入可采集应用态。必须排空所有本地握手输出、核对 USB 完成状态/实际长度，再进入 ARM；**没有已验证的额外命令、额外事件门控或强制等待时间**。参考桥接器还使用约 0.5 s 输出静默判据（附录 C），这是实现行为，不是设备要求；也不能仅以输出过 CCS/Finished 代替 TLS 库成功验握。`0x64` 间歇可达、语义未定（§10 行 3）。
- **分段数量与持续 TLS 处理**：宿主 `TLS_DATA` 的 4/6 次分片、图像外层 `EVT_TLS` 的 11/12 帧与相应总量均是样本；不得以固定数量认定握手或成像成功，也不能仅凭多出一条记录就断言只差分段、内容等价。验收依据是 TLS 库状态、完整且已完成传输的 TLS 字节流，以及解密后的合法应用帧和 §5 像素布局。等待触摸时仍须把 `EVT_TLS` 喂给 TLS 层、排空必要输出并处理 fatal alert/连接关闭；不得把 TLS 错误降格成 no-touch 超时。


**密钥 envelope `[CONFIRMED：050，三次无手指独立 init+TLS run]`**：
- `GET_TLS_KEY` 返回 **121 字节**。三次独立无手指 run 均得到同一字段布局（只记录非敏感的 offset/length，不分发 envelope 或 PSK）：`magic=0x0DEC0DED`；密文 key `offset=28, length=32`；AAD `offset=76, length=13`；signature `offset=89, length=32`；解密后 PSK 长度 `32B`；**offset 60..76（16 B）为未定名区间**（位于 key 与 AAD 之间；本规格未赋予语义，实现**不得**依赖其内容）。
- **头部编码（实现必须按字段切分，不得硬编码偏移）**：121 B 的前 28 B 是 **7 个 little-endian u32**，字段序为 `magic, key_off, key_len, aad_off, aad_len, sig_off, sig_len`（实测 0x0DEC0DED, 28, 32, 76, 13, 89, 32，`89+32 = 121` 闭合）；解析**必须使用头部字段**，否则**硬编码偏移**的实现会误接受（见 `tls-envelope/hardcoded-key-offset-rejected`）；且**必须先做字段范围检查**——合法总长 121 B 下的真正越界例见 `tls-envelope/signature-offset-out-of-range-rejected`（sig_off 89→95 ⇒ 95..127 越出 121 B，拒绝阶段 `field-bounds`，**先于** HMAC）。
- HMAC 认证范围已由运行实现与三次成功校验共同确定为：`AAD bytes || encrypted_key bytes`；**HMAC 密钥 = `SHA256("FPC_HMAC_KEY\0")`**（与 AES 密钥同为 NUL 结尾 ASCII 串的 SHA-256）；摘要为完整 SHA-256，比较 32B。AES-256-CBC 解密密钥为 `SHA256("FPC_SEALING_KEY\0")`，IV 全零。
- **AES 填充（实现必须）**：envelope 的密文段是 **AES-256-CBC *无填充*（NoPadding）**、恰好 32 B（2 块）；解密所得 32 B **直接**作为 PSK。**不得**用 PKCS#7 解填充（本机 OpenSSL 默认设置会因此拒绝有效输入）。
- Linux 050 未观测到 72B envelope；**72B 布局不属于当前设备契约**。**检查顺序（工程约定）**：`长度/magic → 字段范围（含 key 长度是 16 的倍数、签名长度 = 32）→ AES 解密 → HMAC 校验`；任一失败即拒绝，并应能在自测中报告**第一个失败的阶段**（`reject_stage`，见附录 B.3）。长度不是 121B、字段越界、HMAC 不匹配或签名被截断时，必须报错，不能猜偏移或降级到短签名。
**模板保护**（Windows Hello 远程协议）不在开源实现范围内：本机比对不需要加密模板。

## 13. 开源实现建议（独立编写）

1. **传输**：libusb——`libusb_control_transfer` 发命令（`bmRequestType=0x40/0xC0, bRequest=命令 ID`，§3.1 定案）；`libusb_bulk_transfer`（EP 0x82）收帧，**按 §4.4 len 跨包聚合**；轮询读或异步完成回调
2. **TLS 通道**（§8）：初始化后必须完成 TLS-PSK 握手（PSK 来自 `GET_TLS_KEY` envelope 中的 AES-256-CBC 密文，解密密钥 = `SHA256("FPC_SEALING_KEY\0")`、IV 全零；TLS 1.2 + PSK-AES128-CBC-SHA256；ServerHello 需回送非空 `session_id`，实测样例为 32B）。**推荐用 libssl/GnuTLS 等公开实现做 server 端，不要自行实现密码学**。设备→宿主的应用数据经 `EVT_TLS` 帧承载，解密后按 §5 处理（像素参数已定案：偏移 24／stride 112／8-bit／坐标系按 §5 约定）。
3. **libfprint 驱动**：`fpi_device` 接口：`open`(§6 初始化+TLS)、`capture`(§5)、`close`；注册 `10a5:9201`
4. **死像素持久化**：`/var/lib/fprint/<hwid>.deadpixels`
5. **电源**：记录实际 autosuspend 策略与状态；`5000 ms` 是 INF 静态配置，不是设备约束。附录 C 的 `auto` 成功轮不支持“必须改成 on 才能采集”的结论；恢复通信时新建 session/重新握手，异常 reset 的认证限制仍按 §16.4，不能靠固定等待解除。

## 16. 失败、取消与生命周期安全契约（可执行保守行为；覆盖范围与不适用项见 §16.3/§16.4）

本节给出实现者**不得自行发明**的安全行为。它不把未验证的恢复能力写成支持承诺；未知设备状态一律导致当前事务失败并保留诊断。

### 16.1 事件与应用解析
- 收到**未知 `code`**：L2 解析器必须原样交付帧，由 capture 层判本事务失败，不得误当 finger-down/成像成功。第三字段默认原样保留；唯一明确的例外是下一条 `EVT_ARM_RESULT(value=0x64)` 保守失败策略。
- **分片未满不是立即错误**：帧头不足8 B时保留并继续接收；达到8 B即可校验长度，`len <12` 或 `len >65536` 立刻失败。合法长度但头/帧未满时继续按§4.4累积，单次读timeout不清空它。只有事务deadline/取消/连接结束时仍残留不完整帧，才按终止原因报告截断或弃用partial并保留其长度；不得把正常分片误判为协议失败。已知非法长度或不可能的应用消息长度则停止解析，保留尚未消费字节，不逐字节重同步、不丢弃后宣称成功。
- 窗口内未向上层交付 `EVT_FINGER_DWN`：到期后报告触摸等待超时，不能把这条软件观察改写为“操作者没按”或“设备/总线未产生事件”；不发送 `GET_IMG`，不以固定延迟伪造触摸。
- `EVT_ARM_RESULT(value=0x64)`：保留原始字段并终止当前事务，**不命名语义、不诊断硬件好坏**。新会话重试可能恢复，也可能再次失败；不得保证下一轮恢复，不将其自动等同于 §16.4 的锁存现象。
- 已知且与本次采集无关的非 TLS 事件可记录并忽略；未知 code 按首条失败，`EVT_TLS` 在握手、等待触摸及图像阶段都须交给 TLS 层处理。只有成功解密并取得合法应用帧才可报告图像。

### 16.2 TLS、认证与 USB 错误
- envelope 长度不是 121B、字段越界、完整 SHA-256 HMAC 失败或 AES 解密失败：拒绝 session；不得尝试 72B、短签名或猜测偏移。
- TLS fatal alert、意外关闭、Finished/MAC 验证失败或握手事务 deadline 到期：当前 session 失败，保留错误阶段。握手尚未完成不得 ARM；触摸等待期间发生 TLS 失败也必须立即终止，而不是等到 no-touch 超时。单次 USB 读取 timeout 不等于 TLS 失败；参考约 200 ms 读 slice 与默认 30 s 触摸/图像窗口分别计时，不把“单次读 5 s 无数据”当作所有状态的强制失效门槛。
- **握手事务 deadline（工程建议）**：从 `TLS_INIT` 开始推荐 15 s，可配置；不是设备保证，也不与单次 USB timeout、30 s 触摸窗口混用。到期显式失败，不增加无证据的应用 ready 门控。
- USB STALL、当前有效句柄 EIO、异常 ENODEV/断连或控制传输失败：当前事务失败；仅 §6 有界初始化事务中预期的旧连接失效允许受控重取。取消时先请求取消并等待所有已提交 transfer 的实际完成回调；**不要关闭仍有效的当前 USB 句柄**，在其上依次尝试 §16.3 清理命令，清理完成后再关闭句柄/上下文。已断连的旧句柄不可能完成设备命令，记录 cleanup 不可发送及首因后释放，不伪造成功；§6 重取分支只释放已退役句柄。记录请求与完成状态/长度，不将“已提交”当“已成功”。
- **不得发送冗余的标准配置请求**：设备已处于目标配置时**必须**跳过 `SET_CONFIGURATION`（先读当前配置再判断）。冗余请求在本机实测会使 bulk IN 0x82 持续 EIO 并触发设备重枚举，当前与后续会话均不可用（台账 #19/#52）。

### 16.3 取消与关闭顺序
- 用户取消时返回独立的“cancelled”状态（不伪装成 no-finger）：停止 reader/forwarder；若已 ARM，依次尝试 `ARM_STOP`，随后 `ABORT`、`SESSION_OFF`；关闭 TLS socket、OpenSSL 子进程与 USB 资源；join 所有线程；保留 run manifest。**（2026-10-15 实测，宿主侧）**：窗口到期 → 退出码 1、`cancelled=false`、`result_class=no-application-data`；窗口内取消 → 退出码 **130**、`cancelled=true`、`result_class=cancelled`；两者 cleanup 均按上述顺序执行，且 `partial_tail=0`、不伪报成功。
- **清理命令编码**：本支持范围仅用验证模式 `wValue=1`；若已 ARM，`ARM_STOP=0x02`（wLength=4，约定载荷 `12 2f 11 17`），随后 `ABORT=0x03`（wValue=0、wLength=0）、`SESSION_OFF=0x12`（wValue=0、wLength=0）；均为 OUT `bmRequestType=0x40, wIndex=0`。参考成功轮实测返回 4/0/0 B。§16.4 禁用的设备侧录入模式 `wValue=2` 不因本条被允许。
- **默认窗口（工程约定）**：等待 `EVT_FINGER_DWN` 的默认窗口 **30 s**（可配置；图像阶段同用该窗口）；窗口到期 ⇒ 退出码 1、`result_class=no-application-data`；窗口内收到取消 ⇒ 退出码 **130**。
- 普通失败使用同一清理顺序，但保留原始错误阶段与底层 errno。清理失败不得覆盖首个根因。
- `close` 在取消回调与可发送的清理命令均完成后返回；正常的下一次 open 新建 session 并初始化/TLS。历史参考CLI曾验证正常 cancel→capture、同进程两个session各成像和资源退出；这些不是同一FpDevice核心/私有USB对象生命周期的集成证明。异常断连/reset另行终止事务；历史空闲port reset后可find/init/TLS只证明传输恢复，**不是**§16.4异常恢复认证已验证，也不构成自动重试许可。
- **验收范围限制**：上一条是参考 CLI 的历史观测，不是对 libfprint 核心对象、私有 USB 对象与 hotplug 路由的实现证明；“同进程两个参考 session”不等于“同一个 FpDevice close/reopen 已通过”。净室侧必须对当前二进制/库身份和每个生命周期场景独立留证。末轮成功不能覆盖首轮取消失败或 cleanup 新错误。

### 16.4 当前支持边界
- 已验证：协议帧拆包、多帧、非法边界拒绝、121B envelope 完整认证、TLS 握手失败分类、取消/失败时的进程级资源清理（2026-10-15 加强：超时与取消可区分、ARM 前/后两个取消点的清理顺序、同进程 close/reopen 无线程/子进程/fd/USB 句柄残留）。
- **异常 reset 与正常初始化不是同一分类**：本设备内置，物理拔插不适用。§6 明确范围内的正常初始化按其事务分支处理，即使 generation 未知也不单凭此判异常；主机显式 port reset、窗口外非预期 removal 或采集中句柄失效则结束本事务。分类依据是可记录的主机动作与阶段，不是从地址/新对象识别设备内部复位原因的算法。对象归属不能确认则失败；不能以此规则要求每次初始化先做port reset。
- **同一 session 内第二次采集：已验证（支持）**（2026-10-15）：一个会话内两轮 `ARM → EVT_FINGER_DWN → GET_IMG` 各得到一张 `code=8/9880B` 图像（每轮 11 个 TLS 外层帧，结构与单采集轮逐项相同；cleanup 仅一次；退出码 0；两轮像素 99.44% 不同）。**但参考工作流仍是每会话一次采集**，实现不需要该能力。
- **支持范围**：正常单次参考采集和正常取消/关闭已有观测，目标实现须独立验收。**异常port reset/非预期设备重现后的自动恢复认证不在本契约支持范围**；§6普通初始化不是该恢复功能，也不是解除历史风险的证据。设备侧录入模式 `ARM wValue=2`、`END_ENROL(0x13)` 及抬指/重按录入状态机未验证，不得使用或宣称支持。
- **异常会话中途port reset后的锁存观测**：历史受控窗口5/9个无手指会话收到finger-down和图像状数据，提示残留风险，成因未证实。约7 min不是安全上界，等待≥10 min、新会话或正常CMD_INIT均没有经验证的安全恢复保证；一般finger-down本来也不是活体证明。不能用该异常窗口解释当前所有零上报。
- **异常恢复调用的可观测行为（工程契约）**：处理已记录异常port reset/非预期重现的**自动恢复尝试**时，终止本次恢复事务并返回可区分的“不支持异常复位后自动恢复”（逻辑分类 `unsupported-reset-recovery`），不得继续自动ARM、向上层交付正常成像成功或继续认证；原始事件仅作诊断。本契约不提供恢复后安全解除动作或自动重试策略。**不要求驱动发明跨进程持久锁存数据库/无限期全设备封禁机制**：跨进程异常历史可见性与安全恢复管理属于尚未设计/验证的上层能力，不得声称已支持。进程重启、重新open、地址改变或时间流逝不是已证明的安全恢复，也不能被报告为该不支持功能已成功；新一次普通初始化本身仍按§6执行。允许显式、单独授权的传输诊断，但诊断成功不解除认证支持边界。
- 未验证：物理断电恢复、异常 reset 具体成因与安全退出条件。历史故障轮后仍有成功会话并不构成全面恢复支持；不得额外引入设备命令、固定分钟等待或 port reset 来掩盖实现缺陷。

## 附录 B — 向量词汇与像素指标定义（2026-10-17 补齐）

> 说明：正文中出现的 `tools/…`、`tests/…`、`run.json` 等标识仅为**证据编号/来源标注**，不是实现输入（§11）；实现者不需要、也不应依赖这些路径。
>
> 交付包中的 `CLEANROOM_TEST_VECTORS.json` 用声明式描述记录输入与期望；本节给出**复现期望所需的定义与词汇**，使实现者无需外部信息即可判定通过/失败。

### B.1 像素指标（对 112×88、8-bit 灰度图 `P[x][y]`）
- `stddev`：全图像素的总体标准差（分母 N）。
- `row_difference`：**行内**相邻列像素差的**绝对均值**。
- `column_difference`：**列内**相邻行像素差的**绝对均值**。
- `horizontal_correlation`：整图与自身沿 x 轴平移 1 像素后的 **Pearson r**，**只比较重叠区**（111×88 个点；**不回卷**）。任一侧零方差取 0.0。
- `vertical_correlation`：同理，沿 y 轴平移 1 像素（重叠区 112×87，不回卷）。

### B.2 接受判据（**结构筛查**，不等于指纹或活体判定）
- `accepted = max(horizontal_correlation, vertical_correlation) >= 0.85`；随机噪声与全零图必然低于阈值。该阈值源自"行宽 112"的判别（§5 第 2 项），此处沿用为**向量层的结构判据**；**不得**当作指纹质量或活体判据。

### B.3 向量词汇表
- `patterns[].kind`：`counter`（`i % 256` 递增）、`literal`（`hex` 原文）、`inner_header_image`（`header_hex` + 内嵌图像）、`horizontal_ramp`／`vertical_ramp`（可带 `step`）、`ridge`（可带 `period`）、`noise`（可带 `seed`，`random.Random(seed).randbytes(112*88)`）、`zeros`。
- `chunks`：一次读操作实际收到的字节数；`"timeout"` = 本次读超时；`0` = 空读。**成功型向量**的 `expect.timeouts` = `chunks` 中 `"timeout"` 的次数 **+ 1**（流末尾再读一次超时）；**错误型向量**为 `0`。
- `expect.frames[]`：`code` / `unknown`（第三字段）/ `total_len`（含 12B 头）/ `payload_len` / `payload_sha256`，恒满足 `total_len = 12 + payload_len`。
- `expect.held_partial_bytes`：解析停止时仍保留、尚未消费的原始字节数（**不得丢弃**）。
- `expect.messages[]`、`pending_after_first_feed`、`consumed_after_first_feed`：应用层 12B 帧头与消息切分状态；`9880 = 12 + 12 + 9856` 必须精确闭合。
- `expect.error`：协议错误串必须**逐字符**一致。
- `tls_envelope.expect`：`accepted` 或 `detail`（拒绝原因）；有效例要求 HMAC 验签通过且 AES-256-CBC 解出 `psk_b64`。
- **分层（工程约定）**：**分帧层**只校验 12B 头（`12 ≤ total_len ≤ 65536`）并原样交付每条消息（含 `code=8, total_len=22` 这类非图像消息）；**capture 层**才要求**图像消息**满足 `code=8`、`total_len=9880`（`12+12+9856`），否则判失败。两层不得互相替代；向量 `application-message/partial-held-until-complete` 属分帧层。
- **比对口径**：像素指标按声明的小数位（四舍五入到 3 位）比较；`noise` 以 **CPython（MT19937）** `random.Random(seed).randbytes` 为准。
- **合成像素的量化（必须）**：对 `ridge`/`horizontal_ramp`/`vertical_ramp` 按 `公式求值 → clamp 到 [0,255] → 向零截断取整（int()）` 得到字节；**不得**四舍五入（`round()` 会让 `pixels/ridge-accepted` 的 row_difference 变成 26.046 ≠ 声明的 26.033）。
- **envelope 检查顺序**（工程约定）：`长度/magic → 字段范围（含 key 长度是 16 的倍数、签名长度 = 32）→ AES 解密 → HMAC 校验`；`expect.detail` 是**说明性文本**，判定以"是否拒绝"这一事实为准，不按文本比对。
- **`expect.reject_stage`（拒绝例可选）**：取值 ∈ {`total-length`, `field-bounds`, `hmac`, `aes`}，表示**第一个失败的检查点**；实现**必须能在自测中报告该阶段**（错误类型/返回值即可，不要求日志格式）。未给出 `reject_stage` 的拒绝例只要求"被拒绝"（`length-72-rejected` 属此类：按 §8 它可因总长或字段范围被拒）。

### B.4 已知覆盖说明
- envelope 向量覆盖：**总长不符**（`tls-envelope/length-72-rejected`）、**HMAC 篡改**（`tls-envelope/bad-hmac-rejected`，`stage=hmac`）、**硬编码 key 偏移**（`tls-envelope/hardcoded-key-offset-rejected`，`stage=hmac`：验证"必须按头部字段切分"）、**合法总长下的字段范围越界**（`tls-envelope/signature-offset-out-of-range-rejected`，`stage=field-bounds`：sig_off 89→95 ⇒ 95..127 越出 121 B，**必须在 HMAC 之前**被范围检查拒绝）⇒ 范围分支现由**可区分阶段**的向量独立验证；**未**单独覆盖"签名被截断"（规则见 §8/§16.2，实现须按规则拒绝）。
- `tls-envelope/hardcoded-key-offset-rejected` 改动的字节是 key 的 **offset 字段**（28→40），`length` 仍为 32；以 `expect.detail` 为准。

### C.4 下一轮记录与验收（工程约定）

使用统一 `CLOCK_MONOTONIC`，记录 `run_id/op_id/阶段/generation/bus/完整端口链`，每个 USB 提交和完成分别留时间、方向/request/value/index/请求长度/status/actual_length；事件只留三字段与交付时间。提示请求、实测起播/呈现、操作者人工反馈分列，没有测量就填 unknown。不得记录 TLS payload、envelope、PSK、真实图像或图像摘要。

`generation` 是**主机观测标识**：同一完整物理端口链在观测到移除/到达或有独立新设备实例证据时赋新标识；只更换句柄、重复读缓存或两个快照相同不产生新标识。无法验证的代际写 unknown，并另记 handle_id；不把本地计数器冒充设备持久身份或安全判据。

只有本轮取得合法应用帧才把本轮 capture 记为通过；cleanup 成败单列，不覆盖首因。cancel→capture、close→reopen 各轮结果独立，不以最后退出 0 或最后一次 close 代替所有轮次的成像结果。取消请求不等于回调已完成；异步回调/资源生命周期的离线边界闭合后再做受控真机对照，本表不要求现在重复按指。

### C.5 参考 API 语义的离线复核

本次复核环境：Python **3.12.13**、PyUSB **1.3.1**、libusb runtime **1.0.30.12037**、桥接子进程的 OpenSSL CLI **3.6.5**。这是本次只读版本检查，不是旧成功轮已记录的二进制/库身份；旧 run 没有完整版本清单。Python 自带 `ssl` 报 OpenSSL 3.5.6，**不是**该轮使用的 `s_server` CLI，不得混淆。

PyUSB 1.3.1 的 libusb1 后端在 `LIBUSB_ERROR_TIMEOUT` 且 `transferred>0` 时**返回已收长度/字节而不抛超时**；长度为 0 才抛 `USBTimeoutError`，上层继续按 §4.4 聚合。非 timeout 错误不享有这一特例。离线调用本机安装后端的完成处理、只注入合成数据（不打开设备）验证了 `TIMEOUT+12 B → 返回12` 与 `TIMEOUT+0 B → 超时异常`。**该离线 API 验证不证明旧硬件运行中曾发生 timeout+部分数据**；该现象的逐次长度未记录。其他包装 API 不能据此类推为同样语义。

参考工具在等待触摸时继续把所有 EVT_TLS 交给 OpenSSL；其宿主 CCS/Finished 输出后静默标志不是 libssl 的 `SSL_do_handshake()==1`。OpenSSL 状态日志支持该成功轮完成密码学握手，但工具在握手后退出 TCP→USB 转发循环，设备方向的加密 alert 也未逐条审计；参考工具同样存在后握手错误观察盲区，不能作为“所有错误路径都正确”的黄金实现。净室实现应按 §8/§16.2 在每个阶段驱动 TLS 库、排空输出、报告 fatal alert/意外关闭，不照搬盲区，也不增加没有证据的设备等待门槛。
